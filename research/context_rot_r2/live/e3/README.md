# R2-E3 — coding-task scenario suite (live GLM 5.3)

Branch `rot2/w17-e3`. Extends the W7 live-model harness
(`research/context_rot_r2/live/`) to the coding-task scenario family of the
campaign brief, with probes that test ACTION, not recall. The W7
infrastructure is reused unchanged (verbatim Rust prompt constants
`rust_prompts.py`, pipeline mirror `rust_mirror.py`, content-keyed response
cache, length-retry ladder, `ANSWER:` delimiter protocol); all new code
lives in this package as sibling modules.

## What runs

- Pipeline: `prepare_compaction` -> `compact` (real GLM 5.3 summarizer wire
  call, exactly the request the Rust pipeline would send) ->
  `append_compaction` -> restore, per arm, per cycle, on five new coding
  scenarios (TASK-A/C/E/H/F below).
- Prober: after every cycle the restored provider context (compaction
  summary carrier + retained tail) is sent with the scenario's action
  question; the answer protocol demands EXACTLY one line `ANSWER: <value>`
  (missing delimiter = extraction failure, never a model failure);
  temperature 0, 3 repetitions per point, majority >= 2 of 3.
- Baseline: 1 pre-compaction probe per task over seeds + cycle-1 entries
  (the context the cycle-1 summarizer sees).
- TASK-F additionally simulates a process restart after cycle 3.

## Scenarios (deterministic blake2b seeds; golds fixed constants)

| task | test | action-level gold |
|---|---|---|
| TASK-A | constraint during implementation | next file to edit is `src/parser.rs`; the tempting root-cause frame sits in `src/auth.rs`, which the user's constraint forbids touching. Correct = names the parser fix and never asserts `auth.rs` as the edit target. |
| TASK-C | correction after implementation started | approach A (synchronous lock on the order table) is chosen and implemented (tool diff), then corrected: current approach is B (idempotency keys on the request handler) at every cycle >= the correction. |
| TASK-E | evidence near boundary (E4 lineage) | the failing test's exact error `assertion failed: depth == 4096 (got 3072)` is the LAST summarized entry before the cycle-1 compaction cut; gold = that exact assertion (both numbers, expected before actual, within 60 chars, plus a depth/assert/panic keyword). |
| TASK-H | avoid rejected approach | user rejects the whole-report blob cache with a reason; assistant proposes fragment caching / materialized views / per-customer rollups. Acceptable = at least one of those three and never the blob cache. |
| TASK-F | restart | TASK-C semantic (nightly reconciliation corrected to event-driven CDC sync), plus a simulated restart after cycle 3 (session serialize -> fresh reload); gold = CDC stream is current at every cycle. |

Shape per task: 2 arms (default, taskState) x 5 cycles x 1 probe x 3 reps,
plus a 1-rep baseline. Cosmetic values (line numbers, counts) draw from
`blake2b(scenario_id)`; anchors and golds are fixed.

Scenario documents: `r2-e3-task-{a,c,e,h,f}.scenario.json` (regenerated by
every run; identical bytes because generation is deterministic).

## Commands

Credentials are resolved from the two PowerShell scripts named in the
campaign brief (API key + Pomerium JWT); tokens never appear in outputs.

```
cd research
python -m unittest context_rot_r2.live.e3.selftest                       # offline self-test
python -m context_rot_r2.live.e3.run_e3 --arm both                      # full suite
python -m context_rot_r2.live.e3.run_e3 --arm default --tasks A --limit-cycles 1 --reps 1   # smoke
python -m context_rot_r2.live.e3.run_e3 --stage aggregate               # rebuild results.json
python -m context_rot_r2.live.e3.run_e3 --arm typed                     # exit 2: not yet available
```

Every wire call is appended to `raw-calls.jsonl` (request, response, usage,
latency, attempts); identical requests resume from the content-keyed cache.
A budget guard (400 calls, counted from the raw log) stops all chains.

## Configuration

- model `glm-5.3` (SGLang, `max_model_len` 1,048,576), temperature 0.
- summarizer `max_tokens` 8192 with the W7 bounded length-retry ladder
  (8192 -> 16384 -> 32768 -> 65536; 3 of 50 cycles needed the 16384 step
  this run, none went higher), probes 4000.
- prompt variant `v2`, `summary_update_policy=off`, summary budget 3200
  tokens (legacy mode), retained-state anchor enabled (production default).
- concurrency 6 across (task, arm) chains; each chain's cycles and probes
  are sequential (summary-of-summary dependency).

## Scoring (`e3-v1`)

One matcher per probe kind (`probe.py`); each rep gets two scores:

- primary (negation-aware): gold present AND no forbidden term asserted.
  A forbidden term inside an explicit rejection context ("the lock was
  rejected", "not src/auth.rs") is not an assertion.
- strict: gold present AND the forbidden term absent entirely.

`action-file` (A): gold stem `parser`, forbidden stem `auth`; recorded
detail includes the full path set of the answer. `action-approach` (C, F):
positives (`idempot`; `cdc`/`change data capture`/`capture`/`event driven`)
vs forbidden (`lock`; `nightly`). `action-error` (E): required numbers
`4096` then `3072`, ordered, <= 60 chars apart, plus a keyword. 
`action-acceptable` (H): >= 1 of fragment/materialized/rollup present and
`blob` not asserted; per-answer coverage of the three acceptable options is
recorded. Round status: majority over the 3 reps; extraction failures
reported separately, never counted as model failures.

### Findings

1. No measurable action-level rot at this scale, either arm. Five
   compaction cycles do not lose a single action-level fact (next-file
   under constraint, corrected approach, boundary-adjacent exact error,
   acceptable-set exclusion, post-restart approach) when the summarizer is
   the real GLM 5.3. This extends W7-E2's default-arm 100% from
   recall-style probes to action probes, and shows the taskState arm at
   100% here (W7-E2 base scenario: 93.7%).
2. The taskState ledger handled the TASK-C/TASK-F corrections correctly —
   but by pairing luck, not by design. In both scenarios the ledger's
   supersession rule paired the user correction with the old approach-A
   decision (they share specific anchors, e.g. "synchronous"), moved A to
   SUPERSEDED, and kept the corrected approach as ACTIVE CONSTRAINTS.
   This is the same token/position-based rule that INVERTED the correction
   in W7-E2's base scenario (Finding 1 there) and merely muddied it in the
   hard variant (Finding 2). The E3 correction texts were written to read
   naturally, and they happen to pair correctly; the E3 suite therefore
   measures baseline action retention, not the ledger's known failure
   modes. An adversarial variant (corrections that share no anchor with
   the old decision) is future work.
3. TASK-E: the exact error survived all five compactions on both arms, but
   only through the summarizer's verbatim-anchor discipline — the ledger's
   VERIFIED EVIDENCE section never captured the assertion itself. The
   evidence regex takes the FIRST matching line of the tool result
   (`test result: 55 passed; 1 failed`), so the assertion line below it is
   invisible to the ledger; the taskState summary nonetheless carried the
   full failing-test block verbatim in Critical Context (the v2 prompt's
   "preserve exact anchors" instruction). Evidence-near-boundary is thus
   retained by prompt discipline, not by ledger protection (consistent
   with R2-E1 finding 3: evidence extraction is content-regex based, not
   role-based).
4. Ops (W7 finding 3 still applies, milder): 3 of 50 summarizer cycles hit
   the 8192 budget (`finish_reason=length`) and completed on the 16384
   ladder step; reasoning tokens are billed against max_tokens. Max
   summarizer latency 45.3 s (taskState, E); 0 HTTP retries; 0 validation
   resamples.

### Budget accounting

209 wire calls in `raw-calls.jsonl` total, within the ~400-call budget:
155 probes (150 cycle points + 5 baselines), 53 summarizer records
(50 cycle calls + 3 length-ladder retries), 1 pong. Token totals:
probes 158,639 in / 18,646 out (15,991 reasoning); summarizers 140,837 in /
155,060 out (117,196 reasoning).

## TASK-F restart: what is and is not simulated

Simulated: after cycle 3's compaction and probe round, the live session
(all entries, ids, compaction entries with their taskState ledger details)
is serialized to the persisted JSON shape and reloaded into a fresh
`Session` object; the restored provider context must be byte-identical
across the round-trip (asserted; it was, on both arms).

Not simulated (a real restart additionally):
- re-opens the on-disk session store (format fidelity, partial-write
  recovery, checkpoint manifests are not exercised — the round-trip here
  is through the research JSON shape, not the Rust store);
- loses provider-side conversation state (in-flight turns, retry/pacing
  state) — the mirror never had any: it rebuilds the provider context
  from entries every cycle by construction, which is why the restart
  cannot change content and the check is an equality assertion;
- clears kernel/continual-harness state (irrelevant to the mirror);
- re-reads the compaction summary as the first provider message — this IS
  exercised (`build_context` on the reloaded session).

## Adding the typed arm (W15 integration point) — WIRED (R2-E5)

`run_e3.py --arm typed` runs the real typed arm since R2-E5 (branch
`rot2/w29-typedarm`); the former stub is gone. The two documented wiring
points landed exactly as planned:

1. `rust_mirror.arm_settings`: the `typed` arm maps to
   `TASK_STATE_MODE_TYPED` (mirrors `resolve_task_state_mode`,
   compaction.rs); `rust_mirror.prepare_compaction` builds the typed
   ledger over the leaving window and merges it with the previous
   cycle's `details.typedState` (the Python port lives in
   `live/typed_mirror.py`, line-cited to typed_state.rs).
2. `e3/driver.py`: where `render_ledger(task_state)` was called, the
   typed arm renders `typed_mirror.render_allocation(allocate(state,
   min(2048, floor(summary_budget/4))))` as the protected block with
   `TYPED_STATE_INSTRUCTION`, gates on the unsafe allocation before any
   model call, and runs the verify gate (one bounded deterministic repair
   for missing-only findings) after the summary; `details.typedState` /
   `details.typedVerification` persist on the compaction entry.

No scenario, probe, matcher, or aggregation change: the arms are data and
`E3ArmResult`/scoring are arm-agnostic. Results: `live/e5/` (README
section "Part 2"). The e3adv suite accepts `--arm typed` for family C1
only.

## Deviations from the Rust path / W7 harness

Inherited from W7 (unchanged, see `live/README.md`): summarizer wire budget
8192 (formula floor); probe context rendered as chat messages with orphan
tool results flattened to user-role `[Tool result ...]` text; research
probe system prompt (not the production agent prompt); prompt variant `v2`
(the Rust adapter's `arm_settings` leaves `legacy`); single bounded length
retry ladder (no retry pacing/deadlines/checkpoints); deterministic
uuid-shaped session entry ids; `summarizerRequestChars` as UTF-8 bytes.

New in E3 (documented precisely):

1. Filler cycles carry tool results (coding-session texture: status
   update, ack, benign `cargo test` output) and every cycle ENDS with a
   large user message. Reason: with `keepRecentTokens=20`, any tool result
   in the cycle tail moves the cut point onto an assistant entry (split
   turn) — the one shape the W7 mirror never exercised and whose
   `[turn_start, cut)` span would be neither summarized nor kept. The
   cycle-final user message keeps every cut on a user entry (asserted per
   cycle by the self-test), matching W7's validated envelope.
2. TASK-E plants the failing-test tool result as the LAST summarized
   entry of cycle 1 (immediately before the cut); its assistant
   announcement precedes it. The probe then tests post-compaction
   retention of boundary-adjacent evidence.
3. Baseline = seeds + cycle-1 entries (TASK-E's evidence exists only from
   cycle-1 entries; the baseline equals the cycle-1 summarizer's input).
4. Probe repetitions 1+ bypass the content cache (`force_fresh`) so the
   3-rep majority is a genuine resample, not one cached answer thrice.
5. Budget counting reads the append-only raw log, not the in-memory done
   dict (summarizer call ids collide per chain and would undercount by up
   to cycles-1 per chain; caught after the run — the reported 209 is
   recomputed from the log and the guard is fixed for future runs).
6. The taskState ledger sees realistic filler noise (repeated benign
   `test result:` lines dedupe into one evidence entry with a repeat
   count, as production would see repeated CI runs).
