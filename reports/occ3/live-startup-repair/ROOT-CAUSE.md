## 1. Statement

Production sglang 0.5.21 initialises `scheduler.tree_cache` as `UnifiedRadixCache` on all 8 TP ranks. `UnifiedRadixCache` and `RadixCache` are SIBLING classes - both subclass `BasePrefixCache`, neither subclasses the other - and `registered_radix_cache_backends()` is empty, so no flag-only switch to the classic `RadixCache` exists. The OCC-3 install gate in `occ3_sglang/latent_worker.py` (stage `radix_cache`) required `type(scheduler.tree_cache) is RadixCache`, which is `False` for the production default. Every live window therefore declined the native install through a chain of three collapses (worker `LatentError("profile")` -> scheduler reply `unsupported_profile` -> tokenizer receipt `installation_unavailable`), rolled back cleanly before any app mutation, and served an inert app with the original api-key middleware but no occ3 routes: the observed 404-with-valid-key / 401-keyless signature. This is a false rejection of a SUPPORTED default runtime shape (SAFE-BUT-DIFFERENT-REPRESENTATION per the campaign spec), not a security failure.

## 2. The production runtime shape (root-verified)

- `tree_cache = UnifiedRadixCache` on all 8 TP ranks: candidate logs TS3 and TS4 print `Tree cache initialized: source=default impl=UnifiedRadixCache hybrid_swa=False hybrid_ssm=False hicache_attached=False streaming_wrapped=False` on every rank (root-verified; recorded in the shape audit, occ3fix-shape-audit.md, TS4 03:42:49, TS3 02:02:16).
- Sibling classes, verified by `__mro__` in the candidate image: `sglang/srt/mem_cache/radix_cache.py:280` `class RadixCache(BasePrefixCache)`; `sglang/srt/mem_cache/unified_radix_cache.py:165` `class UnifiedRadixCache(BasePrefixCache)` (shape audit; root-verified `__mro__` in-image).
- No registered alternative: `registered_radix_cache_backends()` returns `[]` in the candidate image (root-verified), and the 0.5.21 default factory chain ends in `create_unified_radix_cache(ctx)` for this production config (shape audit). There is no classic `RadixCache` instance reachable without a source-level change.
- The decline was FAST, not a timeout: engine-ready `03:42:50.477Z` -> `Uvicorn running` `03:42:50.606Z` (129 ms; root-verified; decline-map item E5). The 30 s `ControlClient` timeout (latent_backend.py:16, :47-50) never fired.

## 5. Classification

False rejection of a SUPPORTED default shape - SAFE-BUT-DIFFERENT-REPRESENTATION per the campaign spec (root session classification, 2026-10-22), not a security failure:

- The gate did exactly what it was coded to do: an exact-type allow-list check (`type(...) is RadixCache`) evaluated against a class the offline model of sglang 0.5.21 never contained. The production cache is a supported default initialised by upstream's own factory, and its surface covers every occ3 touchpoint (section 4).
- The failure mode is fail-safe by design: decline -> clean pre-mutation rollback -> inert serving with the original auth intact. No security check was bypassed, no unverified code path was reached, no route was mounted, and no data-path request was ever admitted (the second gate, section 7, would have refused descriptor requests independently).
- The defect class is a compatibility false negative plus an observability gap (the three collapses erased the category), not an authorisation or isolation defect.

## 6. Why the offline gates missed it

- **Fake class mocks in the unit tests.** The extension's tests import `occ3_sglang` without a sglang install (tests/conftest.py:3, fake package assembled at :142-176) and inject hand-written `RadixCache` fakes where the gate runs: `tests/test_latent_scheduler_patch.py:124-149` defines `class RadixCache: pass` in a fake `sglang.srt.mem_cache.radix_cache` module and drives `_occ3_validate_received` against it (`state.tree_cache = RadixCache()` passes; a subclass declines); the `64492e8b1`-era worker tests do the same (`tests/test_latent_worker.py:358-414` at `64492e8b1`: `_worker_init_env` fakes the module and builds `NS(tree_cache=(RadixCache() if radix_match else object()), ...)`). The exact-type check was only ever exercised against the fake, never against the real 0.5.21 default.
- **Rehearsals cover docker lifecycle only.** The disposable rehearsal fixtures are pure-Python `http.server` stubs (deploy/v3/rehearsal.py:27-75, `FIXTURE`) driven through nine docker-lifecycle scenarios (rehearsal.py:77-87). No scenario boots sglang, a scheduler, or any cache class.
- **Tiny-boots could not load the real model.** The seven tiny-boot debug attempts against the candidate image all failed on co-resident GPU memory limits (BUG-LEDGER.md, W4-A1 entry), so the scheduler-side shape was never observed live before TS3/TS4.
- **The offline closure never exercised a real image build with the runtime cache.** The offline image-build closure had recorded the runtime limit "No image build" (DEPLOYMENT.md, live-window 1 record), so the real default-cache initialisation was outside every offline gate.

## 7. The second data-path gate (independent, same defect class)

The patched scheduler carries the same exact-type check on the per-request data path: `_occ3_validate_received` (patch `patches/scheduler-cache-ipc.v1.json`, scheduler.py replacement 2 at `64492e8b1` - the state baked into every live candidate image; image `scheduler.py:2820`) opens with

```python
if (type(self.tree_cache) is not RadixCache
        or self.enable_hierarchical_cache or ...):
    raise ValueError("occ3_unsupported_profile")
```

and a failing check sends the request to `_occ3_reject_received` (image `scheduler.py:2806-2812`), aborting the request with `occ3_unsupported_profile`. Even with the install gate fixed, every descriptor-carrying (occ3 attached) request would abort at this gate until it also accepts the unified cache (this is the pre-repair condition that ran in TS3/TS4; the `99b2ebdc9` repair is recorded in section 8). The `mem_cache/common.py` private-path patch itself (occ3_private_match / occ3_release_private_kv) is shape-compatible with `UnifiedRadixCache` (section 4), so the gate condition is the only blocker on this path.
