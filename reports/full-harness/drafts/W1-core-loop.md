## 2. RISK-RANKED GAPS

- **P1 — Sequential tool-batch cancellation leaves dangling tool calls.** agent_loop.rs:1655-1656 and :1691-1692 `break` out of the sequential loop without synthesizing results for unstarted calls; run_loop then exits on the cancellation check at :935-938. The context (and the session history via MessageEnd persistence) keeps an assistant message whose tool calls have no matching tool results. Parallel mode does NOT have this hole (every entry yields a result, even "Tool execution aborted" via agent_loop.rs:2092-2097). `agent_loop_continue` only checks the tail role (agent_loop.rs:684-701), so a later continue can send an invalid conversation to the provider. UNCERTAIN: `crate::core::messages::convert_to_llm` (out of scope) may patch missing results; TS parity unknown.
- **P1 — O(context) deep clones per tool call, per turn, per request.** Full `AgentContext` clone: per deferred parallel tool call (agent_loop.rs:1765), per before_tool_call (agent_loop.rs:1991), per after_tool_call (agent_loop.rs:2214), per turn for `ShouldStopAfterTurnContext` (agent_loop.rs:942-943, also clones `new_messages`), full history clone per provider request (agent_loop.rs:2408), plus 2 partial-message clones per delta (:1469-1476 region). A tool-heavy session pays ~3 full-history clones per tool call per batch; total cost is quadratic in session length. Correctness is unaffected; latency and allocator pressure grow with history. No test or bench guards this.
- **P2 — ExecutionScope accumulates receipts/tasks for the Agent's lifetime.** The Agent owns ONE scope (agent.rs:375, constructed :433). Every provider request registers a `StreamTaskReceipt` (agent_loop.rs:1317) and every tool spawn pushes an `OwnedTask` (agent_loop.rs:2130 -> execution_scope.rs:71-87). Within the audited files there is NO call to `settle`/`reset_after_settlement` (rg over agent.rs/agent_loop.rs/agent_session.rs: zero hits; execution_scope.rs:145-158 defines them). `status()`/`request_cancel()` iterate all accumulated entries (execution_scope.rs:96-114). UNCERTAIN: a daemon-side audit task may call these; if not, this is an unbounded growth + O(n) cancellation cost bug.
- **P2 — `agent_loop_continue` validation is too weak for the cancel/abort states it receives.** Only empty-context and assistant-tail are rejected (agent_loop.rs:684-701). Dangling tool-call tails (P1 above) and custom-role tails pass. The doc comment at :668-671 itself admits "This cannot be validated here since convertToLlm is only called once per turn."
- **P2 — Retry orchestration is outside the audited surface.** `handle_retryable_error`/`is_retryable_error`/`close_retry_metric_group` live in `agent_session/runtime_members.rs:3339/3533/3507` (out of assigned scope). The in-scope call sites (agent_session.rs:7452-7472, :7373-7389) show reset-on-success and metric-group closure, but the retry loop, backoff, and attempt-cap logic are unaudited; transport_retry_tests.rs exists but was out of scope.
- **P3 — `convert_to_llm: None` silently sends an EMPTY message list.** agent_loop.rs:2421-2424 falls back to `default_convert_to_llm_placeholder()` (:1592-1594) returning `Vec::new()`. Direct `AgentLoopConfig` users (not `Agent`, which always installs a converter at agent.rs:426-431) would issue provider requests with no conversation. No warning, no error.
- **P3 — `Agent::process_events` panics outside an active run (agent.rs:1031).** All current emit paths are joined before `finish_run` (run_with_lifecycle awaits the executor first, agent.rs:869-880), but any future detached emitter (e.g. a tool update drain surviving a code change) turns a late event into a process panic.
- **P3 — Deltas before `Start` are silently dropped.** agent_loop.rs:1469-1476: `if *added_partial` guards both the context-tail update and the MessageUpdate emission; a malformed provider stream that emits TextDelta without Start loses content with no diagnostic.
- **P3 — Aborted (STOP_REASON_ABORTED) assistant messages still count toward autonomous usage.** agent_session.rs:7345-7347 excludes only STOP_REASON_ERROR. TS parity UNCERTAIN.
- **P4 — `end_agent_stream_on_error` resolves the AgentEventStream with an EMPTY message list on error (agent_loop.rs:596-608).** Stream consumers cannot distinguish a failed run from an empty one; the failure is only observable via events/state. Matches the TS port intent but untested for the error branch.
- **P4 — OneAtATime queue drain clones all remaining batches (agent.rs:113-118).** Minor; O(n^2) over n batches.

## 3. SUSPECTED BUGS

**SB-1 (P1): Sequential-mode cancellation produces a tool-call/tool-result mismatch in persisted context.**
- Where: `crates/pi-agent-core/src/agent_loop.rs:1654-1656` and `:1691-1692` (`execute_tool_calls_sequential`), consumed by `run_loop` at `:915-938`.
- What looks wrong: the `break` statements skip the remaining `tool_calls` without pushing error results. The assistant message already in context lists N tool calls (extracted at `:911` / `message_tool_calls` :1603-1610); only M<N `ToolResultMessage`s are appended at `:921-924`. The run then ends via the cancellation check at `:935-938`. The state and the persisted session history (MessageEnd persistence path in `process_agent_event`, agent_session.rs:7330-7420) now contain an assistant message with unanswered tool calls whose tail is a toolResult, which `agent_loop_continue` (agent_loop.rs:684-701) accepts.
- Reproduce/verify as a test (wave 2): unit test in `agent_loop.rs` tests: register a sequential tool (or set `tool_execution` Sequential), stream an assistant message with 3 tool calls, cancel the run token after the first `ToolExecutionEnd`, drive the loop, then assert either (a) every tool call id in the final `context.messages` has a matching tool result (proposed fix: synthesize "Tool execution aborted" results for skipped calls, matching the parallel path at :2092-2097), or (b) the loop refuses continue on that context. Today (a) fails; document which behavior is intended.
- Caveat: `crate::core::messages::convert_to_llm` (not in scope) may repair dangling calls at request time; the test should assert at the AgentContext level, which is provider-independent.

**SB-2 (P2, UNCERTAIN): ExecutionScope never settles/resets within core+session code.**
- Where: agent.rs:375/:433 (single per-Agent scope), agent_loop.rs:1317 (register_stream per request), agent_loop.rs:2130 (spawn per tool), execution_scope.rs:96-114 (status/request_cancel iterate ALL historical entries), execution_scope.rs:145-158 (settle/reset never called in audited files).
- What looks wrong: `State.streams` and `State.tasks` grow monotonically; `request_cancel` and `status()` become O(total requests+tools ever run); receipts are never dropped.
- Verify as a test: build an Agent with a faux stream fn, run K prompts each with a tool, then assert `ExecutionScope::status()` cost or internal vec lengths stay bounded (needs a test accessor; today only `#[cfg(test)]` visibility exists — the count probe pattern used at agent_loop.rs:158-172 is the model). Also `rg "settle\(|reset_after_settlement"` the whole repo (out of my scope) to find the intended owner.

**SB-3 (P2): `prepare_tool_call` before-hook abort turns an abort into a TOOL ERROR RESULT in history.**
- Where: agent_loop.rs:1977-2001: `maybe_abortable(before_tool_call(...))` returns the abort error when the token fires mid-hook; the `Err` arm converts it to `create_error_tool_result(&format!("{error}"))` (abort text becomes tool-result content, is_error=true), which is then persisted as a normal tool result message via `create_tool_result_message` :2269.
- What looks wrong: not a protocol violation, but a cancelled run leaves tool results whose text is the abort error string, and the loop still exits via the cancellation check — the abort error is thus recorded as a tool failure (metrics: `record_tool_performance_metric` :1844-1853 classifies outcome Failure unless signal already cancelled; the check at :1849-1852 does mark Cancelled when the token is set, so metrics are fine; only history text is noisy).
- Verify: unit test — cancel during before_tool_call; assert the tool result content is the dedicated abort wording (compare with `execute_prepared_tool_call`'s "Tool execution aborted" :2133-2136) rather than a raw anyhow display.

**SB-4 (P3): `Agent::continue_` with a custom-role tail can issue a provider request whose converted context ends at an arbitrary role.**
- Where: agent.rs:697-706 — custom tail falls through to `run_continuation` when no queued work; `default_convert_to_llm` (agent.rs:258-266) drops Custom messages, so the LLM-visible context ends with whatever preceded the custom message (possibly assistant-with-tool-calls).
- Verify as a test: session-level (or Agent-level with default converter): context = [user, assistant(tool_call), toolResult, custom]; call continue_; assert the converted llm_messages tail is a user/toolResult role or the run is rejected. UNCERTAIN whether real session tails can reach this state (the session drives continue through its own paths).

**SB-5 (P3): stall message drops accumulated partial content from the context.**
- Where: `abort_stalled_stream` agent_loop.rs:1215-1296 replaces the context tail with `create_stream_stall_message` (stream_watchdog.rs:242-304), which never sets `message.content` (defaults empty). The partial that streamed so far is discarded from history; only `partialContentBlocks` count survives in diagnostics (:279-282).
- Intended per comment ("an empty content vector keeps the provider-retry replay guard open", stream_watchdog.rs:386-390 analog), but with retries DISABLED the user-visible history silently loses the partial answer. Verify: run with watchdog trip, retry settings off, assert what the UI/history shows; decide whether a `details.partialText` should be retained.
